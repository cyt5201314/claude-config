# Lark 任务面板

面板是 Lark 里的一个任务清单，用户自己整理任务用，同事也看它了解进度。所以：

- 面板只有这一个。任务不记在别处，也不另建清单。
- 写进去的东西同事看得到。标题和描述写成同事能看懂的话，不写只有本会话才懂的指代。

所有读写都走 `scripts/board.py`，不要直接拼 `lark-cli task …` 写面板：脚本保证每条任务都有分组、大类、项目，并拦住下面「脚本会拦的」那几种情况。

## 能不能用

```bash
python3 ~/.claude/skills/lark-task-board/scripts/board.py snapshot
```

报 `lark-cli 不在 PATH 里` 或 `找不到配置`：这台机器（比如云端会话）不能用。告诉用户，停下，不要改用别的办法记任务。

## 面板结构

| 用户的概念 | Lark 里 |
|---|---|
| 大类、项目 | 两个自定义单选字段。项目属于哪个大类写在配置的 `category_of` 里，建任务只给项目 |
| 状态 | 分组：待整理 / 本周要做 / 进行中 / 等别人。做完用任务自带的「已完成」；配置了 `done_section` 时，标完成的任务还会移到那个分组 |
| 大任务 → 小任务 | 任务 → 子任务。子任务不单独放进清单，否则看板上会多出一张卡 |

实际的分组名、项目名以 `snapshot` 输出的 `sections`、`projects` 为准。

## 加任务：先判定，再给用户看，再写

1. **读面板**：跑 `snapshot`，拿到所有未完成任务（含子任务、描述、依赖）和 `based_on`。
2. **拆**：把用户给的内容拆成候选任务。每条的标题写到能判断「做完没有」；一次做不完的拆子任务。
3. **判定**：每条候选和面板上每条任务比，给出一种判定：

   | 判定 | 什么时候 | plan 里写 |
   |---|---|---|
   | 新任务 | 面板上没有讲同一件事的 | `create` |
   | 重复 | 同一个项目、做完的标准是同一个，只是说法不同或多了细节 | `append`，把新细节补到原任务 |
   | 子任务 | 是面板上某条任务的一部分，那条做完必须包含它 | `subtask` |
   | 相关但独立 | 各自能单独做完，但改同一处、或互相要参考 | `create` + `related` |
   | 被卡住 | 另一条不做完这条没法开始 | `create` + `blocked_by` |

   拿不准是不是重复，按新任务处理，并在给用户的表里标「拿不准」。错合并会让一件事从面板上消失，漏合并只是多一张卡。

   比的是「做完的标准是不是同一个」，不是标题像不像：「订单系统加退款申请」和「退款功能」是同一件；「退款申请」和「换货申请」标题像，是两件。

   面板上已有的任务之间如果也该是父子关系，用 `reparent`，同样列进表里。

4. **给用户看**：列一张表，每行是候选任务、判定、对应的已有任务标题、项目、分组、截止日、一句理由。归不了项目或没有截止日的，分组写「待整理」，表后面一次问完。
5. **用户点头后写**：把 plan 写成 JSON 文件（放 scratchpad，不放仓库），先 `apply --dry-run`，再 `apply`。
6. **汇报**：用 `apply` 输出里的 `url` 给出每条新任务的链接。

用户说「直接记」「不用确认」时，只有判定为新任务的那些可以跳过第 4 步。`append`（合并进已有任务）和 `reparent`（改挂已有任务）每次都要列给用户确认，拿不准的也照样要问：这两种写错了，会有一件事从面板上消失或挪了位置，用户不容易发现。

## 改状态

- 用户说开始做、卡住了、在等谁：`move` 到对应分组。等别人时用 `append` 写清在等谁、等什么。
- 用户说做完了，或者你在本会话里把这件事做完并验证过：`complete`，`result` 写一句可验证的结果。
- 「今天做什么」「还剩什么」：只跑 `snapshot`，按截止日和 `blocked_by` 排，不写面板。

## plan 的格式

```json
{
  "based_on": "<snapshot 输出的 based_on>",
  "ops": [
    {"op": "create", "summary": "…", "project": "<项目名>", "section": "<分组名>",
     "description": "…", "due": "2026-11-21",
     "subtasks": [{"summary": "…", "due": "2026-11-20"}],
     "blocked_by": ["<guid>"], "related": ["<guid>"]},
    {"op": "subtask", "parent": "<guid>", "summary": "…"},
    {"op": "append", "task": "<guid>", "text": "…"},
    {"op": "reparent", "task": "<guid>", "parent": "<guid>"},
    {"op": "move", "task": "<guid>", "section": "<分组名>"},
    {"op": "complete", "task": "<guid>", "result": "…"}
  ]
}
```

`description`、`due`、`subtasks`、`blocked_by`、`related`、`result` 可以不写。`due` 只能是 `YYYY-MM-DD`。guid 只能用这次 `snapshot` 里出现的。

## 脚本会拦的

`apply` 先检查整份 plan，有一条不过就什么都不写（`PLAN REJECTED`），并一次列出全部问题：

- `based_on` 和面板现在的状态对不上：判定之后面板变过，重新 `snapshot`、重新判定，不要只改 `based_on`。
- 新任务的标题和某条未完成任务（含子任务）去掉空格后相同：先确认不是重复。确实是另一件事就把标题改得能区分；用户明确说就要同名，才写 `"same_title_ok": true`。
- 项目、分组不在面板里，guid 不是未完成任务，`due` 格式不对。

同一份 plan 里的 op 按顺序检查：前面标了完成的任务，后面不能再引用；前面改挂成子任务的，后面不能再换分组；一条任务一份 plan 里只能改挂一次，且不能绕成环；`related`、`blocked_by` 里同一个 guid 只能写一次。

还有未完成子任务的任务不能标完成：父任务完成后，它下面没做完的子任务会跟着从面板上消失。用户说大任务做完了，先问清剩下的子任务是也做完了（逐条 `complete`，排在父任务前面）还是不做了（同样 `complete`，`result` 写「不做了」和原因）。

写到一半失败时，输出的 `done` 是已经动过面板的那几条；带 `"incomplete": true` 的那条只写了一部分（比如主任务建好了，子任务或关联没写完）。重新 `snapshot` 看清现状，只补剩下的，不要整份重跑。

## 不做的事

- 不删任务。脚本没有删除；要删，把链接给用户自己删，或者用户点名要你删时再单独处理。
- 不改清单的成员和分享范围，不新建分组和字段选项。用户要加项目时，让用户在 Lark 里加选项，再把它加进配置的 `category_of`。
- 读不到任务评论（没有 `task:comment:read`），所以要留给以后看的信息写进描述（`append`），不写评论。

## 配置

`~/.claude/lark-task-board.json`（不进任何仓库：里面是清单 ID 和项目名）：

```json
{
  "tasklist_guid": "<清单 guid，清单链接里 guid= 后面那段>",
  "category_field": "大类",
  "project_field": "项目",
  "category_of": {"<项目名>": "<大类名>"},
  "done_section": "<放已完成任务的分组名，可以不写>"
}
```

分组和字段选项的 ID 每次从 Lark 现读，不写在配置里。配置和面板对不上（项目名不是字段选项、`done_section` 不是分组）时脚本会直接报错。

写了 `done_section` 时，`complete` 先把任务标完成，再把它移到这个分组；子任务不在清单里，不移。没写就留在原分组。这个分组只放做完的任务，`create`、`move` 不要用它。
