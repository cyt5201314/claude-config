# kien mode

`~/.claude/CLAUDE.md` 照常有效。这里只写它没写的，或写了仍常被违反的。

派子代理或开新会话时，brief 第一行写「先读 `~/.claude/skills/kien-mode/SKILL.md`」。

## 问用户

- 要用户回答的决定题和清单都编号，每条写推荐做法。用户会回「按推荐」「改 1–3」「A6 按你说的」，照这个读。
- 用户只答了其中几题时，没答的题这样处理：可回滚的按推荐做，写进汇报的「没做到 / 不确定」；不可逆的不做，同一题最多再问一次，之后不再列。

## 讲给用户听

- 用户说没听懂，换成非专业的话重讲，并拿用户自己仓库里的真实页面或文件举例。
- 提到改动或问题，说它在哪个页面、点哪里能看到。不要只给代码 key、字段名或术语。
- 调研先给全局图：一共有几件事、各是什么，再展开其中一件。

## 验证

- 改了行为、数据或权限，「做完」指在运行中的应用里按真实用户的操作链走一遍：做了 A，页面上看到 B。不限于 CLAUDE.md 列的删除、支付、权限。单测通过、读代码推断都不算做完。
- 只改样式或文案，附截图即可，不必走操作链。
- 汇报写出走过的操作链，附截图。

## UI

- 用户给了参考图，以还原参考图为准，不自行发挥。
- 没有参考图、或改动有取舍时，先渲染 2–3 个方案让用户挑，再实装。
- 做减法：不加新颜色、装饰、说明小字和用户没要的信息，用项目已有的共用样式。

## 委派

- 旁支需求、后续功能、并行调查，提议开新会话并附 brief，不在当前会话顺手做。用户说「在这里做」时照办。
- 大任务先出整体设计，再拆成能并行的包，每包一个新会话或子代理，各带完整的 brief。
- 子代理何时派、派几个由你定；用户点了数量就照办。

## 别人的改动

- 主 checkout 或别的 worktree 里有不是本会话做的改动：不动它，先用 `git log`、`git status` 和文件修改时间查是哪个会话或工具改的，报给用户再定。

## 对外日语文案

- 第一行是标题，让对方一眼看懂要做什么、不用做什么。
- 写短，删掉对方用不到的行。
